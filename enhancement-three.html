Overview

Database Enhancement of the Weight Tracking Application

Artifact Description

The artifact selected for the database category is an Android Weight Tracking Application originally created for CS 360: Mobile Architecture and Programming. The original version was developed as a single-user mobile application that allowed a person to record weight entries and review basic progress information. Its initial implementation demonstrated the fundamentals of Android interface development and local persistence, but it treated the application as one shared profile and did not provide strong separation between users, a complete account lifecycle, or sufficiently defensive handling of sensitive authentication data.

For the CS 499 enhancement, I expanded the artifact into a multi-user application backed by a structured Room database. The enhanced design introduces user accounts, a separate profile for each account, and weight entries that are explicitly owned by a user. It also adds login and registration workflows, secure password storage, per-user queries, account deletion, password changes, validation, and database-level referential integrity. These changes move the artifact from a classroom prototype toward a design that better reflects professional expectations for data ownership, maintainability, privacy, and security.

Justification for Inclusion in the ePortfolio

I selected this artifact because it provides a clear before-and-after demonstration of my growth in database design and software engineering. The original application had a useful purpose, but its persistence model was limited and tightly coupled to a single shared experience. Enhancing it required more than adding tables. I had to reconsider the data model, define ownership relationships, protect authentication data, update application logic to operate within a user session, and ensure that database operations remained consistent when accounts or records changed.

The most important database improvement is the transition to a normalized, user-scoped schema. The enhanced design uses separate User, UserProfile, and WeightEntry entities. Each profile and weight entry is associated with a specific user identifier. This structure eliminates the original assumption that all information belongs to one global profile. It also allows multiple users to use the same installation without viewing or modifying one another's records. Data access objects use parameterized, per-user queries so the repository requests only the records that belong to the authenticated account.

The artifact also demonstrates relational database principles through foreign keys, cascading deletion, and indexing. The UserProfile and WeightEntry records reference the owning user, and deletion rules remove dependent data when an account is deleted. Foreign-key enforcement is enabled when the database opens, which is important because declaring a relationship without enforcing it can still allow orphaned records. An index on the user identifier improves the efficiency of repeated per-user history queries. These features show that the enhancement considers both correctness and performance rather than treating the database as unstructured storage.

Security was another major reason for selecting this artifact. Passwords are not stored or compared as plain text. The enhancement documentation specifies PBKDF2 with HMAC-SHA-256, a random salt for each user, 120,000 iterations, and a 256-bit derived key. When a password is changed, the application generates a new salt and hash. This implementation demonstrates a security mindset because a database compromise would not immediately expose reusable passwords. The design also limits application permissions by requesting SMS access only when needed and continuing to function when permission is denied or telephony is unavailable.

The artifact was further improved through validation and lifecycle controls. Dates must follow a consistent year-month-day format, weights must remain within realistic boundaries, and account deletion relies on database relationships rather than manually attempting to remove every dependent row. The schema is versioned, and the current course build uses destructive migration as a documented trade-off. Although destructive migration is acceptable for a demonstration build without production data, a production release would require explicit migration scripts and backup testing to preserve user information across upgrades.

Course Outcome Coverage

This enhancement substantially supports program Outcome Four: demonstrating well-founded techniques, skills, and tools to implement computing solutions that deliver value. Room entities, data access objects, repository-based persistence, background execution, indexing, and referential integrity are established techniques for building maintainable Android data layers. The resulting system delivers direct value by keeping each user's health records separate and by making account management predictable.

The enhancement also supports Outcome Five by applying a security mindset to software architecture and data protection. Salted password hashing, session-scoped data access, parameterized queries, input validation, runtime permission handling, and cascading deletion reduce several avoidable risks. Rather than adding security after the database was complete, the enhancement treats authentication, authorization boundaries, privacy, and data cleanup as architectural concerns.

Outcome Three is represented through the evaluation of design choices and trade-offs. I had to choose a relational structure that supported multiple users, determine where relationships should be enforced, add an index where it would improve common queries, and decide how schema migration would be handled during the course milestone. The enhancement also improves correctness by ordering weight history by the recorded entry date instead of assuming that the highest row identifier is always the newest real-world measurement. That correction connects the database design to the algorithmic behavior of the application.

Outcome Two is supported by the narrative, code-review documentation, enhancement summary, and the organization of the artifact for an ePortfolio audience. Outcome One is addressed more indirectly. Clear architecture and documentation make it easier for instructors, reviewers, and future developers to understand the database design and discuss future decisions. My outcome-coverage plan remains focused on Outcomes Three, Four, and Five for this artifact. The final ePortfolio will use the other enhancement categories and the professional self-assessment to demonstrate broader coverage of Outcomes One and Two.

Reflection on the Enhancement Process

The most significant lesson from this enhancement was that database work affects nearly every layer of an application. Adding a User table required changes to the schema, data access objects, repository, session handling, navigation, interface state, and deletion behavior. A database enhancement cannot be evaluated only by whether a table exists. It must be evaluated by whether the application consistently respects the relationships and rules represented by that table.

I also learned the difference between documenting a constraint and actually enforcing it. A foreign key is valuable only when the database engine enforces the relationship during inserts, updates, and deletions. Enabling foreign-key enforcement and demonstrating cascade deletion made the relationship observable and testable. Similarly, an index should be added because it supports a known access pattern. In this application, user-specific weight history is a frequent query, so indexing the user identifier is justified. Adding indexes without a query-driven reason can increase storage and write overhead without providing meaningful benefit.

Password handling was one of the most important challenges because it required both correct implementation and restraint. The application needed to verify credentials without storing recoverable passwords. Salting and repeatedly deriving a key make offline guessing more expensive, while constant-time comparison reduces avoidable timing differences during verification. The enhancement also reinforced that authentication is not the same as data isolation. After login, every profile and history query must still be scoped to the active user. A successful login would not protect privacy if later queries returned all records.

Another challenge was balancing milestone scope with production readiness. The enhanced schema is versioned, but destructive fallback is used for the course build. This allowed the architecture to move forward without spending the entire milestone on migration code for prototype data. The trade-off is potential data loss after a schema change. In a production system, I would replace destructive fallback with tested migrations, create pre-upgrade backups where appropriate, verify rollback behavior, and add instrumentation tests that open older schema versions and confirm that all user relationships and records survive the upgrade.

The process also improved my understanding of recoverability and testing. Database tests should verify more than successful inserts. They should confirm that one user's records are never returned for another user, duplicate usernames are rejected, invalid data does not enter the database, password verification succeeds and fails appropriately, and deleting a user removes dependent rows without affecting other accounts. These tests would provide stronger evidence that the schema and repository enforce the intended design under both normal and adverse conditions.

Overall, the enhancement transformed the Weight Tracking Application from a single-user prototype into a stronger portfolio artifact that demonstrates relational modeling, secure credential storage, per-user data ownership, query efficiency, lifecycle management, and documented trade-offs. The work shows substantial progress toward the database, software engineering, algorithmic decision-making, and security outcomes of the Computer Science program. It also gives me a more realistic foundation for discussing how data architecture supports privacy, reliability, and maintainability in professional software.
