Overview

The artifact selected for the software design and engineering category is my Weight Tracking Android application, which I originally created for CS 360: Mobile Architecture and Programming. The application was developed in Java as a mobile tool for recording weight measurements, setting a goal weight, reviewing historical entries, updating a user profile, and receiving reminders. The original artifact already used several sound Android development practices, including Room persistence, a repository, a ViewModel, LiveData, fragments, RecyclerView, and the Navigation component. However, it operated as a single shared-user application and did not provide account authentication, session management, or complete separation of one user's information from another user's records. Those limitations made it an appropriate artifact for a substantial software design and engineering enhancement.

Justification for Inclusion and Improvements

I selected this artifact for my ePortfolio because it demonstrates the full software-development lifecycle within a project that is understandable to both technical and nontechnical audiences. The application contains a user interface, navigation, application state, persistent storage, background work, validation, notifications, and testing. It therefore provides stronger evidence of my abilities than an isolated programming exercise. The artifact also shows that I can review an existing working application, preserve useful design decisions, identify limitations, and add new capabilities without discarding the original project.

The primary enhancement was the conversion of the application from a single shared profile into a multi-user application. I added registration and login screens, session restoration, logout, password changes, and account deletion. A new User entity and data-access object support authentication, while the existing profile and weight-entry records are associated with the authenticated user's identifier. The WeightViewModel now uses the current session to expose only the profile and entries belonging to the active user. This design improves privacy and provides a clearer boundary between presentation, application state, and persistence.

I also improved maintainability by assigning focused responsibilities to specialized components. LoginFragment and RegisterFragment manage authentication input, SessionManager maintains the signed-in state, PasswordUtils handles credential hashing and verification, SmsHelper isolates optional text-message behavior, and InsightsFragment presents calculated progress information. The repository continues to coordinate database and business operations away from the user-interface thread. The Navigation component controls transitions between authentication and application destinations, and LiveData allows the fragments to observe changes instead of manually synchronizing every screen.

Additional engineering improvements include validation for usernames, passwords, dates, phone numbers, and realistic weight ranges; context-based runtime permission handling; a date-selection control rather than unrestricted date entry; account-management controls; history search; CSV export; and targeted RecyclerView updates through DiffUtil. I added unit tests for password handling, analytics, date processing, and measurement conversions. Together, these changes improve usability, testability, maintainability, privacy, and reliability while preserving the application's original purpose.

Course Outcome Coverage

The enhancement met the outcome-coverage plan established in Module One, with the strongest evidence supporting Course Outcomes Two, Four, and Five. Course Outcome Two is demonstrated through the code-review presentation, the written enhancement narrative, meaningful class and method organization, and documentation that explains design decisions for different audiences. The application itself provides visual communication through a consistent screen flow, focused forms, status messages, and an Insights destination that translates stored data into information a user can understand.

Course Outcome Four is demonstrated through the use of Java, Android Jetpack components, Room, LiveData, ViewModel, RecyclerView, DiffUtil, repository-based data access, background execution, and JUnit testing. These tools were not included merely to increase technical complexity. Each supports an application goal: Room provides managed persistence, LiveData supports reactive screens, the ViewModel preserves application state, the repository limits direct database access from the user interface, and tests make important logic more repeatable and verifiable.

Course Outcome Five is demonstrated through salted PBKDF2 password hashing, per-user data ownership, foreign-key enforcement, cascade deletion, runtime permission checks, input validation, and graceful behavior when SMS capability is unavailable or denied. The original enhancement plan anticipated stronger authentication, reduced exposure of sensitive information, safer permission behavior, and improved database integrity. Those goals were met. The updated outcome plan also recognizes partial coverage of Course Outcome Three because I evaluated trade-offs involving architecture, usability, performance, migration behavior, and implementation complexity. Course Outcome One is supported through GitHub documentation, the code review, and written design explanations, but collaboration is not the primary focus of this individual mobile artifact.

Reflection on the Enhancement Process

The most important lesson from this enhancement was that improving software design does not always require replacing the entire architecture. My initial plan described a broad refactoring because I expected the original artifact to concentrate most responsibilities in one activity. A closer review showed that the application already contained fragments, a ViewModel, a repository, Room entities, and observable data. The better engineering decision was to preserve those strengths and extend them. This required me to distinguish between structural problems that actually existed and changes that would only make the project appear more complex.

The multi-user enhancement was the most significant challenge because authentication affected nearly every layer of the application. Adding a User entity was only the first step. Session restoration, navigation, profile ownership, entry ownership, queries, account deletion, password changes, and screen refresh behavior all had to agree on the active user. A defect in any one of those areas could expose another user's records or leave the interface in an inconsistent state. This reinforced the value of clear data ownership, centralized state, and small components with specific responsibilities.

Security decisions also required practical trade-offs. Passwords are now stored as salted hashes instead of plain text, and optional SMS behavior follows runtime permission rules and degrades gracefully when permission or telephony is unavailable. The Room database currently uses a destructive fallback when the schema version changes. That approach is acceptable for this course demonstration because the artifact contains test data, but it would not be appropriate for a production application containing real user history. A production release would require tested, non-destructive migrations, stronger recovery procedures, and broader instrumentation and security testing.

Overall, the enhancement demonstrates meaningful progress in software design and engineering because the final artifact is not simply larger than the original. It has clearer user boundaries, stronger security controls, more focused components, better test coverage, and a more complete account lifecycle. The process improved my ability to evaluate an existing codebase, revise a plan when the evidence changes, manage design trade-offs, and connect technical implementation choices to maintainability, privacy, and user value.
